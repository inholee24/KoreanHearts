# KH1 에서 가져오는 규칙과 방식 (Re:COM 적용판)

KH1 한글화(2026-06 ~ 11, 실험 56차, 번역 약 7,800줄)에서 확정된 번역 규칙·작업 방식·교훈을 Re:COM 에 맞게 정리한 것이다. 원문은 [../../kh1/docs](../../kh1/docs) (특히 work-history 6-50 이후, terminology, known-issues, build-process). KH1 과 다른 점은 **Re:COM:** 으로 표시한다.

## 0. 가장 중요한 원칙: 분석으로 검토한다 (게임 실행은 최소)

사용자가 원하는 것은 **파일과 exe 를 정확히 분석해서, 되도록 게임을 켜지 않고도 결과를 검토할 수 있는 상태**다. 사용자 원문:

- (10-28) "exe 분석을 싹 다 해줘, 매번 exe 뜯어보지 않고 필요에 따라 바로바로 필요한 정보 사용할 수 있게"
- (10-29) "그부분만 네가 리버스엔지니어링 할 수는 없어?" / "그 자막 오차도 직접 계산해서 보정해줘"
- (10-29) "exe 파일을 더 뜯어봐서 어떻게 돌아가는지 알아와줘. 이왕이면 내가 직접 테스트하는 횟수가 줄어들었으면 좋겠어"
- (11-02) "나한테 일일이 매번 확인하게 만들지 말고 네가 직접 확인할 수 있을때까지 **분석해**"
- (11-04) "항상 exe를 뜯어봐"

사용자 결정의 근거와 시행착오 전체는 [conversation-lessons.md](conversation-lessons.md).

그래서 순서는 항상 다음과 같다.

1. **데이터 + exe 분석으로 규칙을 확정한다.** 포맷·공식·배치·한도는 exe 의 해당 함수(로더, 디코더, 그리기, 측정)를 읽어서 정한다. 데이터 몇 개가 맞는다고 일반 규칙으로 단정하지 않는다 (Re:COM PoC 3: 가나만 보고 공식을 확정 -> 게임 5회 실행 낭비. 공식은 exe 0x25C480 에 그대로 있었다).
2. **분석 결과를 도구로 만든다.** exe 규칙대로 화면을 그려 보는 시뮬레이터(KH1 `sysfont_sim.py`), 원본과 전수 대조하는 검증기(`verify_build.py`), 창 넘침 검사기(`fixwin_check.py`), 자막 오프셋 계산(`recenter`). 검토는 이 도구의 출력(그림·수치)으로 한다.
3. **분석 결과를 문서·색인으로 남겨** 다음에 다시 뜯지 않는다 (exe 색인 `re_index_recom`, file-formats.md, names 표).
4. **게임 실행은 마지막 확인용으로만, 묶어서, 꼭 필요할 때.** 분석·시뮬레이터로 결과를 이미 예측한 상태에서 "예측과 같은지" 한 번 본다. 한 번 켤 때 여러 항목을 함께 확인한다. 가설을 찾으려고 게임을 반복해서 켜지 않는다. 타이밍에 민감한 상태(대기 영상 등)에서 포커스를 뺏는 조작을 하지 않는다.
5. **사용자에게 화면 확인을 떠넘기지 않는다.** 분석으로 끝까지 확인하고, 분석으로 도저히 안 되는 장면(가 볼 방법이 없는 장면)만 목록으로 남겨 유저 플레이 제보로 넘긴다 (KH1 known-issues "유저 플레이로 확인할 대사").

## 1. 결정권과 진행 방식 (사용자 결정)

- **번역은 Claude 가 끝까지 한다. 검토는 나중에 유저들이 한다** (2026-10-29). 중간에 번역 확인을 요청하지 않는다. 사용자에게 묻는 것은 "다른 곳과 달라서 확인이 필요한" 경우뿐이고, 그것도 먼저 리버스엔지니어링으로 풀어 본다.
- 게임 조작 도구(`recom/tools/recom_gamectl.py`)는 위 0-4 의 마지막 확인용이다.
- 배포물에 **원본 게임 파일·영어 원문을 넣지 않는다.** 저장소 번역 표는 key + ko 만 (`tables.py strip/expand` 방식). 설치는 사용자 PC 에서 원본을 꺼내 빌드.
- 시어터(별도 exe, Panacea 미지원)는 한글화하지 않았다. **Re:COM:** 타이틀 메뉴의 THEATER 도 같은 Theater.exe 일 가능성이 높다 -> 같은 결정 적용 (확인 후).
- 커밋·푸시는 사용자가 요청할 때만. `main` push = 사용자에게 바로 배포되므로 검증된 상태만.

## 2. 번역 규칙

### 용어

- 기준: **시리즈 한국 정발 표기 (KH3 한국어판)**, 디즈니 = 디즈니 코리아 공식, FF 캐릭터 = FF 한국어판. 공식 1.5+2.5 한국어 자막(2027 초여름 예정)이 나오면 다시 맞춘다.
- 시리즈 공통 용어는 [KH1 용어집](../../kh1/docs/terminology.md) 을 그대로 쓴다 (도날드, 스퀄, 홀로우 바스티온, 키블레이드 이름 등). Re:COM 고유 용어만 [terminology.md](terminology.md) 에.
- 같은 원문 용어는 문맥이 달라도 같은 표기. 일반 명사 heart = 마음, darkness = 어둠, light = 빛, world = 세계 (고유 명칭 "월드" 와 구분).
- 근거가 약한 표기는 `확인 필요` 로 표시하고, 바꿀 때는 용어집과 번역 표를 함께 고친다.
- 디즈니 작품명은 한국 공개 제목. 마법 단계는 파이어/파이라/파이가 식. 기술·블록·아이템 이름은 음역 + 원래 접미사 유지 (예: 프로텍트-G).

### 말투

- 소라·리쿠·카이리·도날드·구피끼리는 반말, 도날드·구피는 임금님께 존댓말. 소라·도날드·구피는 미키를 "임금님", 리쿠는 "미키 왕".
- 상점 주인·안내 NPC·**시스템 안내문은 존댓말** (`~요`, `~니다`). 짧은 알림·버튼은 명사형 ("HP 회복.", "세이브 실패.").
- 모그리 말끝 "쿠뽀". 구피 감탄사 "Gawrsh" = "어휴", "A-hyuck" = "아휵".
- 보고서(안셈 리포트)는 문어체 ~다, 줄거리 요약은 서술체.
- **Re:COM:** 기억의 성 인물(조직 XIII 등)의 말투는 첫 등장 장면을 보고 정해 terminology.md 에 적는다.

### 구조 보존

- 제어 코드·아이콘·플레이스홀더(`%s` 등)·끝 코드의 **순서와 값을 원문 그대로** 둔다. 줄바꿈 위치는 바꿔도 된다.
- **선택지 메시지는 줄 수 유지** (줄 하나 = 선택지 하나).
- **이름이 끼워 들어가는 자리(`%s`, 아이템 이름 삽입 코드) 뒤에 받침에 따라 달라지는 조사를 바로 붙이지 않는다.** "몇 개를", "하나" 처럼 피하거나 `(으)로` 형태. **Re:COM:** `%s` 가 많다 (예: "Start game as %s.") -> 같은 규칙.
- 원문이 알파벳 자체를 쓰는 퍼즐·코드(책장 퍼즐 K, S, A …), 개발용 문자열(Debug, Dummy, Test), 약어(Lv., HP, MP, EXP, AP), 숫자·기호만 있는 줄은 원문 유지.
- 같은 원문이 특정 위치에서만 다른 뜻이면 **위치별 번역 표**(file, idx, en, ko)로. key 별 번역보다 우선, en 이 원본과 다르면 빌드가 멈춘다.
- 원문 사실 오류도 원문대로 옮긴다 (예: 구피 데뷔 연도).

### 길이·폭

- 게임에 **자동 줄바꿈이 없었다** (KH1, exe 확인). 줄은 줄바꿈 코드로만 나뉜다. **Re:COM:** 미확인 -> 확인 전까지 같은 가정.
- 번역 줄 폭은 원문 최대 줄 폭 이내를 기본으로, 넘으면 그 x1.15 와 고정 상한 중 큰 값 (KH1 대화창 440 = 한글 약 19자). 폭은 글꼴 폭 표로 계산한다 (눈대중 금지).
- **고정 크기 창**(스크립트가 크기를 정하는 말풍선, 초상화 옆 쪽 등)은 내용이 넘쳐도 창이 안 커진다 -> 전수 검사 도구를 만든다 (KH1 `fixwin_check.py`).
- 원문을 가운데 맞춤한 오프셋은 번역 폭에 맞춰 **빌드 때 자동 보정**한다 (번역 표는 그대로, KH1 `recenter`).
- 파일·버퍼 크기 한도가 있는 것(고정 버퍼에 덮어쓰는 파일)은 원본 크기를 넘지 않게 빌드가 검사한다.

## 3. 작업 방식

### 파이프라인 (KH1 에서 확정, Re:COM 도 같은 틀)

```text
원본 추출 (pkgextract)  ->  번역 표 펼치기 (tables expand: key+ko + 원본 = 전체 표)
  -> 빌드 (글자 배정 + 글꼴 그림 + 폭/매핑 표 + 메시지 파일)  ->  verify (원본과 전수 대조, 문제 0)
  -> mod 적용  ->  인게임 확인  ->  work-history 기록
```

- 손으로 코드를 배정하지 않는다. **번역 표 하나 + 빌드 도구**가 매번 원본에서 새로 만든다 (KH1 26차).
- 번역 표: 같은 원문은 한 줄 (key = 원문 해시). 다시 추출해도 ko 열은 key 로 보존.
- 글자 배정은 빈도순, 빌드마다 바뀔 수 있다 (글꼴·표·메시지를 한 번에 같이 쓰므로 문제 없음).
- **verify 는 필수**: 바뀐 메시지는 모두 번역이 있는 원문이고, 글자표로 해독하면 번역문과 정확히 같아야 한다. 길이·크기 한도, 원본과 같아야 하는 파일도 확인.
- 번역 일감 도구 (KH1 `tr_batch.py`): `next N 접두어` -> `bNNN.tsv` (key<TAB>ko) -> `apply` (구조 검사: 코드 순서, 줄 폭, 허용 글자) -> `reuse` (글은 같고 코드 값만 다른 줄) -> `stats` (진행률, 새 글자 수 / 칸 상한). 묶음마다 build + verify + work-history.

### 실험 방식

- **실험보다 분석이 먼저** (0번 원칙). 게임 실험은 분석으로 가를 수 없을 때만 하고, 그때도 exe 에서 관련 함수를 먼저 찾아 예측을 세운 뒤 한다.
- **가설 하나, 실험 하나, 기록 하나.** 실험 전에 "화면 A 면 확정, B 면 기각" 표를 적고, 결과는 성공·실패 모두 work-history 에.
- 실험에서 예상과 다른 결과가 나오면 바로 다음 실험을 하지 말고, exe·데이터 분석으로 원인을 먼저 찾는다 (Re:COM PoC 3 에서 □ 결과 뒤 추측 실험을 두 번 더 한 것은 잘못).
- **"안 보임" 이면 코드 경로를 파기 전에 그림 형식·색·위치부터 배제** (KH1 3~8차 결론이 색 문제로 전부 무효가 됐다).
- 같은 길이 바이트 치환 표식(`BASECT`/`UKCTDL`)으로 어느 파일을 읽는지 먼저 가린다 (Re:COM PoC 1).
- 화면 비교는 눈이 아니라 픽셀 측정으로 (KH1 55차: 사다리꼴 말풍선은 원본과 같았다).
- 인게임 검색: 게임이 그 화면에 있을 때 메모리에서 문자열을 찾아 실제 출처를 가린다 (KH1 50차 PAUSE: 그림이 아니라 낱글자 메시지였다).

### 보존·안전

- 원본(`data`, 게임 폴더)은 읽기만. mod 폴더에만 쓴다. 변경 전 백업 또는 재생성 스크립트.
- **재사용 스크립트는 저장소 `tools/` 에.** 세션 임시 폴더 스크립트는 사라진다 (KH1 2026-10-28 전부 유실).
- ModsManager 의 Build / Restore / Fast restore 는 mod 폴더를 지운다 -> 쓰지 않는다. 실행은 게임 직접 실행(Panacea).
- 시험용 게임 폴더는 하드링크(`D:\Projects\kh_testgame`)로, 실제 게임 폴더의 설정은 건드리지 않는다.

### 글꼴

- 한글 글리프는 **맑은 고딕**으로 렌더링하고 **원본 글리프의 색·테두리·알파 규칙을 재서 그대로** 따른다 (KH1: 대화창 = 회색 채움 + 검정 테두리 + 알파 계조, sysfont = 테두리 없음). **Re:COM sysfont:** 흰색 + 알파 계조, 테두리 없음, 높이 약 35/40px (PoC 2).
- 한글 아래 끝(기준선)을 영문 대문자 아래 끝에 맞춘다 (KH1 41차 "배틀" 이 "배튼" 으로 가려짐).
- 게임이 텍스처를 크게 줄여 그리면 획이 들쭉날쭉해진다 -> 축소를 흉내 내 미리 보고, 필요하면 살짝 블러 (KH1 53차).
- 글자 간격(전진 폭)은 원본 전각 글자와 비교해 정하고 인게임에서 확인 (KH1 46~47차).
- 글꼴이 둘 이상이다 (KH1: 대화창 / 시스템 / 설정 메뉴). 한 문자열이 두 글꼴로 그려지는 경우(이름 삽입)는 **두 글꼴에서 같은 코드**로 배정한다 (공유 배정). 어느 화면이 어느 글꼴인지 먼저 확인.

### 범위 점검 (KH1 에서 나온 텍스트 종류)

대사·이벤트 / 상점·시스템 메시지 / 메뉴 이름·설명 / 장소 이름 (세이브 파일에 문자열로 남음 -> 예전 세이브는 영어) / 도움말·튜토리얼 / 사전·보고서 / 설정 메뉴 (SettingMenu.pkg, 1.5+2.5 공용) / 그림 속 글자 (타이틀 버튼, 명령 메뉴 제목, 월드 제목 부제, 미니게임) / 영상 자막 / 글자 사이를 제어 코드로 벌린 문자열 (P A U S E).
**Re:COM:** 같은 목록 + 카드 이름·설명, 방 카드(맵 카드) 이름, 기억의 성 층 이름. SettingMenu 는 KH1 에서 이미 한글화한 공용 파일이므로 중복 작업하지 않는다 (같은 파일인지 확인 후).

## 4. Re:COM 에서 이미 다른 점

- 텍스트 = `@CTD` (.ctdl), 1바이트 ASCII + 2바이트 Shift-JIS, 줄바꿈 0x0A. 자동 줄바꿈 여부 미확인.
- 글자 코드 -> 글리프 매핑·폭이 데이터(FFMW binl)에 있다 -> exe 메모리 패치 없이 갈 가능성이 높다.
- 한글 칸: sysfont 899, evtfont 1,280 (recom_capacity.py; 처음 963/1,339 는 게임이 직접 그리는 글자 칸을 빼먹은 값, 2026-11-09). 코드는 한자 영역(lead 0x88~0x9F, 0xE0~) 사용. 공식은 file-formats.md (lead 0x85/0x86 없음).
- **교훈 (2026-11-09):** "영어 텍스트 파일이 안 쓰는 칸 = 빈 칸" 이 아니다. exe 가 직접 그리는 글자(키보드 표, `×%02d` 같은 서식 문자열)도 지켜야 한다. 칸을 고를 때 exe .rdata 의 문자 표·서식 문자열까지 조사할 것.
- 영어 모드는 UK 파일을 읽는다 (US 아님).
