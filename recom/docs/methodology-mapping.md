# KH1 한글화 방법론 → Re:COM 적용 검토 (2026-11-04)

## Re:COM 에서 더 쉬운 점

1. 글꼴 칸·폭·매핑이 모두 **데이터 파일**이라 실행 중 메모리 패치가 필요 없다 (KH1 은 텍스처 크기·일본어 배치·표 확장을 메모리로 고쳤다).
2. 글자 코드 규칙이 하나다 (KH1 은 대화창과 UI 가 다른 표·다른 코드).
3. 영상 자막이 데이터 파일이다.
4. 한글 칸이 처음부터 넉넉하다 (sysfont 963, evtfont 1,339 vs KH1 영어판 대화창 873 에서 시작해 확장).

## Re:COM 에서 먼저 풀어야 할 분석 과제 (게임 실행 전에)

1. ~~레이아웃 -> 글꼴 선택 규칙~~ **해결 (2026-11-04)**: 글꼴 = 텍스트 객체 플래그 비트 12, evtfont 는 지미니 일지·카드·방 UI 만. 모든 한글을 두 글꼴에 그리는 설계로 판정 불필요 (한글 종류 <= 963 이면).
2. **레이아웃 필드 뜻** (exe): 창 위치·크기, 정렬, 자동 줄바꿈 여부. 창 넘침 검사기의 전제.
3. **원본 CTD 와 `US/` CTD 중 어느 것의 UK .ctdl 을 읽는지** (exe 경로 규칙). key 로 둘 다 바꾸면 결과는 같지만 범위 계산에 필요.
4. `.imz` 그림 형식, `MVS` 자막 항목 구조(시각 단위), CTD 밖 텍스트(카드 이름 등)의 위치.

## 결론

KH1 방법론의 **틀(원본 꺼내기 -> 키+한글 표 -> 빌드 -> 전수 검증 -> 시뮬레이터 검토 -> 마지막 게임 확인 -> 원본 없는 배포)** 은 Re:COM 에 그대로 적용된다. 바뀌는 것은 파일 형식 처리(CTD, FFMW, MVS, imz)와 제어 코드 규칙이고, KH1 에서 가장 어려웠던 부분(텍스처 용량, 메모리 패치)은 Re:COM 에 필요 없을 가능성이 높다. 분석 과제 1 은 해결, 2 는 원문 대비 줄 폭 규칙으로 우회 가능 (레이아웃 +0x1A 단위는 추론). 남은 큰 확인은 한글 종류 수 <= 963 (번역 후 집계).
