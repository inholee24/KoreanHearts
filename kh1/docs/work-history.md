### 6-1. 실행 결과 1 (2026-09-21) — 메시지 `E1 E2 E3 58 49 57 58 68`

화면 (스크린샷 `images\1.png`):

```text
Sligh가ly raises
Üßà가es가.
```

**해석 (정정 후)**

- `E1 E2 E3`은 레코드 **193, 194, 195**이다. 표에서 각각 `Ü`(U+00DC), `β`(U+03B2, ß 모양), `à`(U+00E0)이고 화면과 정확히 일치한다.
- 뒤의 `58 49 57 58 68`은 `t e s t .`이고, 아틀라스의 `t` 셀이 기준선 패치로 `가`이므로 `가 e s 가 .`으로 보인다.
- 바이트 8개가 글자 8개로 정상 디코드되었다. 오정렬도 렌더러 이상도 없었다.

**원인은 내 계산 오류**: 레코드 221 = `0xDD`, `msg = rec + 0x20 = 0xFD`인데 `0xE1`을 썼다.

**이 실험으로 새로 확정된 것**

1. `msg = rec + 0x20`이 상위 바이트에서도 성립한다: `E1→193 Ü`, `E2→194 β`, `E3→195 à` (화면 확인).
2. `0x80` 이상 바이트도 `0xE3`까지는 **2바이트 선행 바이트로 소비되지 않고** 단일 글리프 코드로 처리된다.
3. 표와 아틀라스에 레코드 221–223을 수정해도 다른 글자 표시에 영향이 없다 (6-2).

**철회한 것**

- "`Slightly`의 `tl`이 깨졌다"는 내 오독이다. 이는 **아틀라스에 이미 들어 있던 `t→가` 기준선 패치**(knj0 `t` 셀 = `가`)이며, `가`가 `t`보다 넓어서 옆 글자 `l`과 겹쳐 보인 것이다. 이전 분석에서 knj0의 38행이 4배 확대에서 벗어난다는 사실(=`t` 셀 밴드)을 이미 확인했었으나 연결하지 못했다.
- 이전 가설 H1(Shift-JIS 선행 바이트), H2(폭·코드포인트 값), H3(공유 버퍼 덮어쓰기): 근거가 없어졌다.

### 6-3 결과 (스크린샷 images\3.png) — 실패, 그러나 정보 있음

```text
Sligh가ly raises

```

- FD FE FF 자리에 **글자가 없고 폭도 차지하지 않는다** (2행이 원본 Defense.의 D와 같은 x에서 시작).
- 뒤의 ense.는 온전하다. 즉 종결자가 아니라 **무시(또는 제어코드로 소비)** 된다.
- 결론: **0xFD–0xFF는 글리프 코드가 아니다. 레코드 221–223은 1바이트 후보에서 제외.**
- 기존 메시지 문맥이 부합한다. UK_SAWDMSG.BIN에서 0C 14 0E FD FF + 지명 텍스트처럼 FD/FF는 명령 **인자**로 쓰이고, UK_PresentMessage.bin의 0C FF 68 05 …도 마찬가지다. 0x00=종결, 0x01=공백, 0x02=줄바꿈, 0x0B/0x0C/0x0E=명령이다.
- 안전한 글리프 범위는 0x20–0xE3까지 확인, 0xE4–0xFC는 미확인.

### 교훈 (이번 세션)

1. **16진 바이트를 손으로 계산하지 않는다.** 스크립트가 `rec + 0x20`을 계산하게 하고, 적용 직후 표를 역조회해서 "이 바이트가 어느 레코드를 가리키는지"를 출력해 확인한다.
2. 화면에서 이상해 보이는 것은 **먼저 기준선 상태와 대조**한다. 기준선에 이미 있던 패치(`t→가`)를 손상으로 오인했다.
3. 예상 밖의 글자가 나오면 그 글자를 표에서 역조회하면 실제로 어디를 호출했는지 즉시 알 수 있다. 이번에는 이 방법으로 원인이 확정되었다.
### 6-4. 테스트 4 — 2바이트 코드를 캔버스 안의 빈 셀로 검증 (2026-09-21 적용, 결과 대기)

**이전 2바이트 실험들이 답을 못 준 이유:** 레코드 512 이상을 가리켜서 셀 위치가 knj0 캔버스(1024×1024) 밖(행 24 = y 1552)이었다. 어떤 결과가 나와도 "코드가 안 통한다"와 "그릴 곳이 없다"를 구분할 수 없었다.

**이번 설계:** 07-22 README의 가설 공식 `index = ((b0<<8)|b1) - 0x1820`이 맞다면 `19 20 → 256`, `19 21 → 257`이다. 셀 공식 `col = rec%21, row = rec/21`을 그대로 쓰면 rec 256/257은 (col 4/5, row 12) → knj0 @1024 y 784, 즉 **캔버스 안의 빈 영역**(y 720–1023 미사용)이다.

**16차 화면:** 상점 주인 대사 `How may I help you?`가 `hXlp`, 선택지가 `I wan가가 buy. / I wan가가 sXll. / NXvXr mind.`로 나오고 **상점이 정상적으로 열렸다.** (`가`는 옛 `t→가` 기준선 패치.)

**레코드 문법 정정:** `08`은 뒤따르는 바이트에 따라 길이가 다르다. `08 07 14 00 43 es, sir.`에서 5번째 바이트 `43`은 인자가 아니라 **첫 글자 `Y`**이다 (`Yes, sir.`). `08 0A 00 00 00 02 Oh…`에서는 5바이트 제어 코드다. exe 점프 테이블의 `08 = 5`는 이 후자의 경우에 해당하는 것으로 보인다 `추론`. 상점 대사 레코드는 `<070c>|00|`로 시작하는 형태와 `08 07 14 00 <첫 글자>` 형태가 섞여 있다. 마지막 글자 뒤에는 `04 0A 00 00 00`(끝 제어 코드)이 온다.

### 6-36. exe 분석 — 창 폭은 UI 폰트 표(`US_font_data_tbl.bin`)의 `+6`으로 잰다

도구: 가상환경 `D:\Projects\openkh_venv` (capstone, pefile, pillow). 스크립트 `tools\re\find_imm.py`, `find_ref.py`, `dis.py` (exe 읽기 전용). 주소는 모두 RVA.

**확정 (디스어셈블):**

- `-0x1820` 디코드가 있는 텍스트 루프 14곳. 2바이트 판정은 `b0 < 0x20` (그리고 `b0 >= 0x15`, `0x18`은 `(b1<<8)-0x1820`으로 별도 처리).
- **`0x2D0E10` = 문자열 폭 측정 함수.** 글자마다 `폭 += ((rec[idx].+6 << 4) + 전역간격) * r14 / r11`, 끝에서 `>> 4`. 1바이트·2바이트 모두 같은 표를 쓴다.
- `rec` = 전역 포인터 `0x2E16BE0`. 유일한 쓰기는 `0x2D15D6`, 값은 정적 배열 `0x2E16BF0`. 바로 뒤에서 언어 ID(`[..+0x274]`, 0/7이면 JP)에 따라 **`exchange/US_font_data_tbl.bin`**(JP는 `FM_font…`)을 이 배열에 읽는다 (문자열 `0x3EFEB8`).
- 같은 표의 `+6`을 쓰는 다른 루프 (`0x2CFDC1`~`0x2D013A`, `0x2EBF6F`~`0x2EC670`)는 UI 글꼴 그리기로 보인다 `추론`. `0x2D0C37`, `0x2D35F0`은 표의 `+8`(유니코드)로 변환하는 함수다.

**원인 `추론`(20차로 검증):** 한글 칸의 UI 표 `+6`은 원래 자리 글자의 값이다. idx 256~259는 **1** (원래 전각 공백 `81 40`), idx 126~139는 1~17. 대화창은 `UK_kanji.knj` 폭(22)으로 그리지만 선택지 창은 UI 표로 재므로 2바이트 글자가 거의 0폭으로 측정된다.

### 6-48. exe 분석 — 대화창 글꼴 용량을 늘릴 수 있는가 (2026-10-29)

목적: 조합형(자모 겹치기) 대신 **완성형 한글 글리프를 충분히 많이** 넣을 경로가 exe 구조상 있는지 확인. 상세는 [exe-analysis.md](exe-analysis.md) 5절.

확인한 사실 (디스어셈블, `확정`):

- `0x18d130` (언어 설정): 영어 등 = 페이지당 16줄, 줄 높이 32, **글자 수 1344**. 일본어 = 21줄, 줄 높이 24, **글자 수 1764**.
- `kanji_cell_xy` `0x175AE0`: 페이지(0~3)는 **텍스처를 바꾸지 않고** 같은 텍스처 안에서 U +512(비트0), V +512(비트1)로 옮긴다. 즉 페이지 0~3 = 1024 x 1024 텍스처의 사분면. 페이지 4 이상은 처리하지 않는다.
- `kanji_load` `0x176430`: kanji_buf 로 **512 x 512** 텍스처를 만들고, **일본어일 때만** 텍스처 폭·높이 필드(`+0x94/+0x96`)를 2배(1024)로 바꾼다.
- HD 교체(`0x10bdf0`, `0xe1680`): DDS 는 "버퍼의 파일 내 오프셋" 키로 붙는다. kanji_buf = 오프셋 0 = `UK_kanji_knj0.dds`. DDS 해상도는 자유 (원본 1024, 우리 것 4096).

