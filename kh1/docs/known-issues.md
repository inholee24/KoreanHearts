## 미확인 — 우선순위 순

### 1. 글자 용량과 글자 집합 설계 (가장 큰 결정)

대화창에서 **새로 쓸 수 있는 빈 셀**은 다음과 같다 (원본에서 폭 0, 잉크 0 확인).

| idx | 개수 | 코드 |
|---|---:|---|
| 126~139 | 14 | 1바이트 `0x9E`~`0xAB` |
| 221~223 | 3 | 1바이트 `FD FE FF` |
| 256~314 | 59 | 2바이트 `19 20`~`19 5A` |
| 315~335 (row 15) | 21 | 2바이트. 정식 원점으로는 캔버스 안이나 아래가 미검증 (4px 잘림) |

합계 **76~97칸**. 여기에 영문 대화에서 안 쓰이는 라틴 악센트(idx 190~217 부근) 등을 재사용하면 더 늘릴 수 있으나 **번역 대상 전체에 필요한 한글 음절 수는 아직 집계하지 않았다.** 페이지 1~3(idx 336~1343)은 폭 테이블은 있으나 **HD DDS(knj0/knj1)에 그림이 없어** 현재 쓸 수 없다 (10차: idx 377이 폭만 있고 비어 있음. knj1 사분면의 해당 셀에 올바른 색으로 글자를 그려 두었는데도 안 나옴).

**일본어판과의 비교 (2026-09-21 분석):**

| | 일본어판 `data\kh1\kanji.knj` | 영어판 `exchange\UK_kanji.knj` |
|---|---|---|
| 파일 길이 | 264,192 (`0x40800`) | 263,616 (`0x405C0`) |
| 폭 테이블 | 1920칸 중 **1764칸이 채워짐 (idx 0~1763 연속)** | 1344칸 중 828칸 (4블록 반복) |
| 비트맵(`0x40000` B) 사용률 | **95.5%** | 25.6% |

- 엔진은 일본어판 글꼴로 **최소 1,764글자**를 다룬다 (`추론`: 언어 ID 0/7일 때 `exchange/JP/kanji.knj`를 로드, exe 문자열 확인). 영어판 경로의 한계는 폭 테이블 1344칸과 셀 계산 함수의 4페이지다.
- `remastered\kanji.knj`에는 FR/GR/IT/SP/UK의 DDS만 있고 **JP는 없다.** 일본어 글자는 DDS가 아니라 파일 안의 PS2 비트맵으로 그려진다 `추론`.
- PS2 비트맵 (`0x40000` B = 4bpp, 팔레트 `0x40004`): **선형 디코드(256폭, 12x16 셀)로는 글자가 나오지 않았다.** PS2 GS 특유의 뒤섞인 배치일 가능성이 높으나 해독하지 않았다 `미확인`. 이 배치를 풀면 페이지 1~3(및 일본어판 수준의 확장)에 글리프를 넣는 경로가 열릴 수 있다.
- **(2026-10-29 exe 분석으로 갱신)** 페이지 1~3이 안 나온 원인은 PS2 비트맵이 아니라 **텍스처 크기**다. 영어판은 512 x 512, 일본어판만 1024 x 1024로 만들고 페이지 1~3은 그 사분면이다. 영어판 텍스처를 2배로 하면 열릴 가능성이 높다 (미검증). [exe-analysis.md](exe-analysis.md) 5절, [work-history.md](work-history.md) 6-48.

**용량 보험 후보 (글자 수가 모자랄 때):**

1. **페이지 1~3 열기**: PS2 비트맵 배치 해독 (위 참조). 성공 보장 없음.
2. **조합형 (자모 겹쳐 그리기)**: 음절을 초성·중성·종성 셀 2~3개로 나눠 **전진 없이(폭 0) 같은 자리에 겹쳐** 그린다. 셀 수백 개로 11,172자 전부 표현 가능. 전제: **폭 0 글리프가 그려지고 겹치는지** (12차 실험 `6-21`), 문자열 길이가 2~3배가 되므로 각 파일이 길이 증가를 허용하는지, 글자 하나마다 출력 지연이 있으면 표시 속도가 느려지는 것.
3. 영문자 셀 재사용: 번역 후 필요 없는 라틴 글자 자리(대화창 idx 0~220 중 상당수)를 한글로 교체. 다만 이 텍스트에서 실제로 쓰이는 라틴이 있으면 남겨야 한다.
**조합형 설계 (13차에서 검증한 내용):**

- 실제 폰트로 음절을 그린 뒤 **초성/중성/종성 영역을 잘라** 조각 셀로 만들고 폭 0으로 겹치면 폰트 원래 음절이 그대로 재현된다 (미리보기와 13차).
- 초성 모양은 받침 유무만이 아니라 **모음의 방향과 폭**에도 좌우된다. `ㅏ`옆의 `ㄹ`은 넓고 `ㅕ`옆의 `ㄹ`은 좁다. 서로 다른 음절에서 자른 조각을 섞으면 `력`이 엉킨다. 따라서 초성은 **세로 좁은 모음(ㅏㅓㅣ) / 세로 넓은 모음(ㅐㅑㅒㅔㅕㅖ) / 가로 모음(ㅗㅜㅡ 등) / 겹모음** x **받침 유무**로 나눠야 한다 (고전 8벌).
- 셀 수 추정 (모든 조합을 만들 경우): 초성 19 x 8 = 152, 중성 21 x 2 = 42, 종성 27 x 2 = 54, 합계 약 **250칸**. 실제로는 번역문에서 쓰이는 (자음, 벌) 조합만 만들면 훨씬 적다 (예: 받침 있는 겹모음 옆의 `ㅋ`은 거의 안 쓰임). 숫자·기호로 남길 셀(약 60칸)을 빼면 페이지 0에 약 250칸이라 **빠듯하다.**
- **추가 발견 (14차):** 위치는 모음 부류(ㅏㅓ / ㅕ / ㅗ / ㅜ / ㅡ가 서로 다름), 초성의 복잡도(ㅇ vs ㅈ, 준에서 확인), 받침 유무 모두에 의존한다. 조각을 다른 음절에서 잘라 쓰면 재현 오차가 12~52%였고, 같은 음절에서 자르면 0%였다. 따라서 조각 부류를 세분해야 하며 셀 수가 위 추정보다 늘 수 있다.
- 각 조각의 폭(T): 초성은 0, 받침 있는 모음은 0, 받침 없는 모음과 종성은 음절 폭(약 22).
**규모 대조:** 필요 고유 음절 약 1,200~1,800자(추정)는 대화창 페이지 0에서 확보 가능한 셀(수백 개)보다 크다. 따라서 **완성형만으로는 부족할 가능성이 높고, 조합형(12차에서 겹침 성공)이 사실상 필요하다.**

결정할 것: 번역 범위(일부 UI/아이템 설명 vs 대사 전체), 글자 집합(빈도 기반 부분집합 vs 조합), 필요 시 캔버스 확장.

### 2. 대화창 텍스트의 출처 — **대사 위치를 찾았다 (2026-09-21)**

**스토리 대사는 `remastered\<월드>.ard\<언어>_<이름>_ard*.binl` 에 있다.** 예: `remastered\tw11.ard\UK_tw11_ard3f3.binl`.

- 헤더: `45 76 4d 73 67` + 언어 2글자 = **`EvMsgUK`** (영어), `EvMsgFR` 등. 언어별로 `UK_`, `US_`, `FR_`, `GR_`, `IT_`, `SP_` 접두어 파일이 따로 있다.
- 본문은 **대화창과 같은 1바이트 코드**(`idx+0x20`)다. 예: `Well, well, as I live and breathe.⏎If it isn't Pinocchio.`. **구두점 코드는 대부분 미확인이다.** 화면으로 확인된 것은 `0x68` = `.` (상점 `Defense.`, 한글 문장 끝 `.`)뿐이다. 이전 문서의 `0x5F=.`, `0x60=?`, `0x68=!`, `0x69=,`, `0x71='`, `0x6E=-` 는 **US_font_data_tbl.bin의 유니코드 필드와 문맥으로 짐작한 것이며 검증되지 않았다.** 대화창 글리프의 정체는 표가 아니라 **knj0의 셀 그림**이 정하므로 (UI 글꼴 표와 순서가 다를 수 있음) 아틀라스 셀 idx 0~220을 직접 보고 확정해야 한다.
- **(2026-10-29 갱신)** 문자표와 `EvMsg` 구조, 제어 코드 길이는 확정됐다 → [file-formats.md](file-formats.md) 1절, 1-1절. 위 구두점 짐작은 틀렸다 (`0x5F = !`).
- 메시지 앞뒤에 제어 코드가 있다 (`08 0A 00 00 00`, `0B 00 <x> 00`, `07 0C 00` 등). 의미는 미확인.
- 같은 월드의 여러 이벤트 파일이 **같은 내용을 복제**한다 (`UK_tw11_ard3f3.binl` = `UK_tw11_ardb.evdl` 등). `.evdl`(7,378개)은 바이너리 목록이며 같은 텍스트를 담는 것으로 보인다 `미확인`.
- 영어 파일은 `UK_`(2,153개 `.binl`/`.evdl`)와 `US_`가 모두 있다. 게임이 `pcReleaseLanguage: en`에서 어느 쪽을 읽는지는 확인 필요 (`exchange`는 `UK_`였다).

**분량 (영어, `UK_*.binl`의 `EvMsg` 파일 기준)**

| 항목 | 값 |
|---|---:|
| `EvMsg` 매직 파일 | 1,074개 (내용이 다른 것 **78개**, 합계 1.27MB) |
| 고유 메시지 조각 | **6,158개** |
| 영문자 합계 | **약 133,000자** (단어 약 32,800) |
| 메시지 평균 길이 | 21.6자 (20자 이하 2,083개, 20~40자 2,988개, 100자 이상 약 20개) |

주의: 메시지는 `00`으로 나눠 센 조각이라 일부는 문장의 일부일 수 있고, 메시지가 조금씩 다른 변형이 별개로 세어졌을 수 있다. 상점/거미/보물 등 `exchange` 계열(약 18,000자), 메뉴/저널(`menu\md_dic_msg.kmb`), 스킬·아이템·장소 이름 등은 별도이며 **이 값에 포함되지 않았다.**

**한국어 환산 (추정, 오차 큼):** 샘플 1건(24자 -> 10음절)의 비율 0.4를 쓰면 대사만 약 5.5만 음절이고 다른 텍스트를 더하면 6~8만 음절이다. 이 규모에서 고유 음절은 **약 1,200~1,800자**로 예상된다 (일반적인 한국어 텍스트 통계에 기댄 추정이며 이 게임 대본으로 집계한 값이 아니다).

**길이 변경 (2026-09-21 확정):** 글자 구간(마지막 글자 뒤, 끝 제어 코드 앞)에 바이트를 넣어 메시지 길이를 늘려도 스크립트가 어긋나지 않는다 (17차). 번역문 길이 제한이 없다. 삭제(길이 감소)는 미검증이나 같은 원리로 안전할 것으로 보인다. 같은 길이 치환도 안전하다 (16차).

**미조사:** `EvMsg` 내부 구조 (메시지 수/오프셋 표가 있는지, 길이를 바꿔도 되는지), 제어 코드의 의미, `menu\` 쪽 텍스트(`md_dic_msg.kmb` 등 `.kmb`), `dh01.ard\tmp.dat`(영어 패턴 439회) 등.
### 3. UI 글꼴(상점 목록, 메뉴)의 한글화 경로
