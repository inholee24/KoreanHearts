## 1. 메시지 파일 인코딩 `확정`

대상: `exchange\*_item_shop_msg.bin` 등 `exchange` 이하 메시지 `.bin`.

Shift-JIS도 UTF-8도 아닌 **1바이트 커스텀 코드**다. 값은 폰트 테이블 레코드 번호에 대응한다.

```text
message_byte = font_table_record_index + 0x20
```

검증 (`UK_item_shop_msg.bin` + `exchange\US_font_data_tbl.bin`):

| msg 바이트 | → 레코드 | 테이블 내용 |
|---|---|---|
| `0x21`–`0x2A` | 1–10 | `０`–`９` (U+FF10–U+FF19) |
| `0x2B`–`0x44` | 11–36 | `A`–`Z` |
| `0x45`–`0x5E` | 37–62 | `a`–`z` |
| `0x58` | 56 | `t` |
| `0x68` | 72 | `．` (U+FF0E) |
| `0xE1` | 193 | `Ü` (U+00DC) — 화면 확인 |
| `0xE2` | 194 | `β` (U+03B2, ß 모양) — 화면 확인 |
| `0xE3` | 195 | `à` (U+00E0) — 화면 확인 |

구분자:

- `0x01` = 공백 `확정`
- `0x02` = 줄바꿈 `추론` (실험 README의 기대 표시가 2줄이었고 디코딩 위치가 일치)

실제 디코딩 예 (`UK_item_shop_msg.bin` 오프셋 5):

```text
3C 49 57 58 53 56 49 57 01 24 21 01 32 3A 01 53 4A 02 53 52 49 01 47 4C 45 56 45 47 58 49 56 68
R  e  s  t  o  r  e  s  _  3  0  _  H  P  _  o  f  ⏎  o  n  e  _  c  h  a  r  a  c  t  e  r  .
```

`0x80` 이상 바이트도 `0xE3`까지는 2바이트 선행 바이트로 소비되지 않고 단일 글리프로 처리됨을 화면으로 확인했다 (2026-09-21).

### 2바이트 코드 `확정` (exe `msg_layout` 디스어셈블 + 18차·25차 화면, 2026-10-29)

선두 바이트 `0x19`~`0x1F` 이면 2바이트 글자다.

```text
index = ((b0 << 8) | b1) - 0x1820     예: 19 20 -> 256, 1B 0B -> 747, 1C 1D -> 1021
```

- **`b0 = 0x1A` (idx 480~735) 는 쓸 수 없다.** `b0-0x19 = 1` 이 공백 코드 비교에 걸려 공백으로 처리된다 (`0x176F80`).
- `0x18 xx` 는 `idx = (xx-0x19)*256 + 0xE0` 인 별도 형식 (용도 미확인).
- 상한 idx 2015. 실제로 그려지는 범위는 글꼴 텍스처에 따름 (영어 512 배치 = 페이지 0 = idx 0~335, 1024 배치 = idx 0~1343. [exe-analysis.md](exe-analysis.md) 5절).

### 대화창 1바이트 문자표 `확정` (knj0 셀 그림, 2026-10-29)

코드 = idx + 0x20. 도구: `tools/evmsg.py` 의 `LATIN`.

| 코드 | 글자 |
|---|---|
| `20` | `―` (긴 줄) |
| `21`~`2A` / `2B`~`44` / `45`~`5E` | `0`~`9` / `A`~`Z` / `a`~`z` |
| `5F`~`6F` | `! ? & % + - × / * . , ・ : ; … – ‒` |
| `70`~`79` | `~ ' " „ ( ) [ ] < >` |
| `7A`~`9D` | 아이콘 (별, 화살표, 버튼 기호, 아이템 모양 등) |
| `9E`~`AB` | **빈 칸** (14) |
| `AC`~`C9` | 장식 글자, 로마 숫자 등 |
| `CA`~`F8` | `¡ ¿` 와 악센트 라틴 (`À`~`ü`), `F9` = `°` |
| `FA` / `FB` / `FC` | `—` / `»` / `«` |
| `FD`~`FF` | **빈 칸** (3) |

이전 문서의 `0x5F=.`, `0x60=?`, `0x68=!` 등의 짐작은 틀렸다. `0x5F = !`, `0x60 = ?`, `0x68 = .`, `0x69 = ,`.

## 1-1. `EvMsg` (`.binl`) 구조 `확정` (exe `0x1A43A0` 의 메시지 스캐너 `0x1A45D0`, 2026-10-29)

```text
"EvMsg" + 언어 2바이트("UK") + u32 메시지 수 N + 메시지 N개 (순서대로, 오프셋 표 없음) + 잔여/패딩(CD)
```

- 메시지 번호 = 순서. 각 메시지는 `0x04` 또는 `0x00` 에서 끝난다 (끝 바이트 포함). 그래서 길이를 바꿔도 된다 (17차).
- 코드 길이: `05 06 07` = 3바이트, `0B 0D` = 4바이트, `0A` = 다음이 `00` 이면 4바이트 아니면 2바이트, `09 0C 0E`~`1F` = 2바이트, 나머지(`01` 공백, `02` 줄바꿈, `03`, `08`, `20` 이상) = 1바이트.
- 일부 파일은 N개 뒤에 이전 내용의 찌꺼기가 남아 있다 (게임은 읽지 않음).
- 검증: 원본 EvMsg 7,379개 중 7,378개(JP 1개 제외)를 이 규칙으로 잘라 다시 합치면 바이트 단위로 같다. UK/US 메시지 758,758개는 `show`/`encode` 왕복이 모두 같다.
- 도구: `tools/evmsg.py` (파서), `tools/evmsg_export.py` (번역 표), `tools/build_ko.py` (적용본 생성). [build-process.md](build-process.md).

## 2. `exchange\US_font_data_tbl.bin` `확정`

8,960 B = **560 레코드 × 16 B**.

```text
[0..1]   구 코드      상위 바이트 00 = ASCII, 그 외 = Shift-JIS
[2..3]   u16 X        아틀라스 좌표가 아님. 아래 주의 참조
[4..5]   u16 Y        아틀라스 좌표가 아님
[6..7]   u16 폭(advance)
[8..9]   u16 UTF-16 코드포인트 (LE)
[10..15] 0
```

검증 예:

| 레코드 | `[0..1]` | `[6..7]` | `[8..9]` | 의미 |
|---|---|---|---|---|
| 11 | `00 41` | 11 | `41 00` | U+0041 `A` |
| 19 | `00 49` | 7 | `49 00` | U+0049 `I` |
| 33 | `00 57` | 15 | `57 00` | U+0057 `W` |
| 56 | `00 74` | 9 | `74 00` | U+0074 `t` |
| 1 | `82 4F` | 11 | `10 FF` | U+FF10 `０` |
| 72 | `81 44` | 8 | `0E FF` | U+FF0E `．` |
| 280 | `82 A0` | – | `42 30` | U+3042 `あ` |

**`[8..9]`에 유니코드 코드포인트가 들어 있다.** 한글 음절 U+AC00–U+D7A3을 그대로 쓸 수 있다.

### 주의: `[2..3]`/`[4..5]`는 아틀라스 좌표가 아니다 `확정`

X는 `8 + 288k` (k=0..13, 14종), Y는 `8 + 384k` (k=0..9, 10종)로 **14×10 격자**를 이루며 레코드 140개마다 `(8,8)`로 되감긴다. 하지만 실측한 아틀라스 격자는 **21×11**이다(아래 4절). 두 격자는 일치하지 않는다.

~~실제 글리프 위치는 레코드 번호로 결정된다~~ (위의 21x11 은 대화창 knj0 이었다). **40차 정정:** `[2..3]`/`[4..5]` 가 실제 소스 좌표다 (1/16 PS2px). `[7]` = 페이지 (하위 니블 CSA: 1 이면 u+256, 상위 니블 1 = PSM 4HH: v+256), HD 좌표 = 2배. sysfont DDS 1024 = 512 사분면 4개 x 14x10칸(36x48). 확장(1024 레코드, 2048 DDS)은 [exe-analysis.md](exe-analysis.md) 5-1절.

### 페이지 구성 `확정`

`[8..9]` 코드포인트 기준으로 560 레코드가 140개씩 4구간으로 나뉜다.

| 구간 | 레코드 | 내용 |
|---|---|---|
| 0 | 0–139 | ASCII, 전각 숫자, 기호 |
| 1 | 140–279 | 확장 라틴(악센트), 기호 |
| 2 | 280–419 | 히라가나 (U+3042~) |
| 3 | 420–559 | 가타카나, 반각 |

### 여유 슬롯 `확정`

`[8..9]`가 `U+3000`(전각 공백)인 레코드가 **150개**. 1바이트로 주소지정 가능한 범위는 레코드 0–223 (msg `0x20`–`0xFF`)이다.

| 레코드 | 개수 | 아틀라스 셀 | 주소지정 |
|---|---:|---|---|
| 138–163 | 26 | 다른 글리프가 그려져 있음 | 1바이트 |
| 221–223 | 3 | **비어 있음** | 미확정 (FD–FF; 7절 참조) |
| 224–230 | 7 | **비어 있음** | 2바이트 필요 |
| 231 이상 | 114 | 미확인 (knj1 영역) | 2바이트 필요 |

**레코드 221/222/223 (msg `0xFD`/`0xFE`/`0xFF`)** 이다. 2026-09-21 실험에서 FD FE FF가 무시된 것처럼 보였으나, **수정한 표가 게임에 적용되었는지 확인되지 않았으므로** 그 결과로 221–223의 사용 가능 여부를 판단할 수 없다 `미확정`. 디스어셈블상 0xFD는 정상 1바이트 글리프 코드(레코드 221)다 (7절).

## 4. 폰트 아틀라스 `확정`

### 파일 관계

- PS2 원본: `data\kh1\kanji.knj` (264,192 B), `data\kh1\exchange\UK_kanji.knj` (263,616 B)
- HD 교체본: `data\kh1\remastered\kanji.knj\*.dds`, `data\kh1\remastered\exchange\UK_kanji.knj\*.dds`
- DDS는 1024×1024 B8G8R8A8 (헤더 128 B + 4,194,304 B)
- **두 경로의 DDS는 바이트 단위로 동일**하고 FR/GR/IT/SP/UK 5개 언어 파일도 전부 동일하다. 고유 이미지는 `knj0`, `knj1` **2장뿐**이다.

### 격자 (빈 행/열 측정으로 도출)

**knj0** — 1024×1024

```text
21열 × 48 px   (0 .. 1008)
11행 × 64 px   (원점 y ≈ 16)

cell_index = record_index
col = record_index % 21
row = record_index / 21
x   = col * 48
y   = 16 + row * 64
```

**knj1** — 1024×1024, 512×512 사분면 4개. 각 사분면은 같은 21×11 격자의 1/2 축척(열 24 px, 행 32 px). **네 사분면은 픽셀 단위로 완전히 동일하다** (알파 차이 0, 원본 기준). 즉 knj1은 knj0과 같은 231개 레코드(레코드 0–230)의 축소본을 2×2로 복제한 것이며, 레코드 231 이상의 글리프 그림은 knj0/knj1 어디에도 없다 `확정`. knj0은 11행(y 16–719)만 쓰고 y 720–1023(4행)은 비어 있어 같은 공식이면 레코드 231–314가 들어갈 자리다 `미확인`.

### 검증 근거

1. 빈 열 경계가 전부 48의 배수(48, 96, 144, …, 960)에 위치하고 내용이 x≈1007에서 끝난다 → 21열 × 48.
2. 빈 행 경계 간격이 ≈64 px이고 구간이 11개 나온다.
3. 테이블 `[6..7]` 폭과 실측 잉크 폭의 상관계수 **r = 0.732** (n=195).
4. 개별 확인: `I`(폭 7) 실측 최소 20, `W`(폭 15) 실측 최대 39, `M`(13) 33, `i`(7) 소문자 최소 12.
5. `t` = 레코드 56 → 셀 (14, 2) → **x 672, y 144**. 2026-06-25 `t→가` 패치가 사용한 좌표와 같고, 현재 적용본에서 원본 대비 변경된 영역의 실측 위치와도 일치한다.

### 4096 업스케일본

현재 `mod\kh1`에 올라간 DDS는 4096×4096이다. 원본의 **정확한 4배 최근접 확대**이며(1024행 중 38행만 예외 — `t` 셀 밴드), 좌표는 전부 ×4로 환산한다.

```text
knj0 @4096: x = col * 192,  y = 64 + row * 256
```

## 7. 글리프 디코드 루틴 (exe 디스어셈블) `확정`

`KINGDOM HEARTS FINAL MIX.exe` (ImageBase `0x140000000`, `.text` RVA `0x1000`). 표 로드가 RVA `0x2D1609`에서 `US_font_data_tbl.bin` / `FM_font_data_tbl.bin`을 참조하고, 글리프를 그리는 루틴이 RVA `0x2CFD50`–`0x2D0251`에 있다. capstone으로 디스어셈블해 읽었다.

문자열 바이트 `al`의 처리:

```text
al <  0x15                  점프 테이블 (제어 코드 0x00..0x14, 인자를 가짐)
al == 0x18                  ecx = (다음바이트 << 8) - 0x1820      ; 0x2CFDC1
0x15..0x17, 0x19..0x1F      ecx = ((al << 8) | 다음바이트) - 0x1820   ; 0x2D0128, 2바이트 소비
al >= 0x20                  ecx = al - 0x20                       ; 0x2D0134, 1바이트 소비
공통 (0x2D013A)             record = 표 + ecx * 16
```

- 따라서 `19 20`은 제어 코드가 아니라 **레코드 256**을 가리키는 2바이트 글리프다. `1A 20`은 512, `1B 20`은 768.
- `0xFD`는 `0xFD - 0x20 = 221`, 정상 1바이트 글리프 코드다.
- 2026-07-22 README의 공식 `((b0<<8)|b1) - 0x1820`은 exe에서 확인된다.

레코드 필드 중 렌더러가 읽는 것:

| 오프셋 | 크기 | 용도 (코드 근거) |
|---|---|---|
| `[+2]` | u16 | 원본 텍스처 X. 그리기 구조체 `+0x20`에 저장 |
| `[+4]` | u16 | 원본 텍스처 Y. 그리기 구조체 `+0x24`에 저장 |
| `[+6]` | u8 | 폭. `<<4` 후 배율을 곱해 전진량과 소스 폭 계산 |
| `[+7]` | u8 | 상위 니블로 테이블(`0x52A6F8`)을 조회, 하위 니블은 별도 필드로 |
| `[+8..9]` 유니코드 | – | 이 루틴에서는 읽지 않는다 |

X 피치 288 = 18 × 16, Y 피치 384 = 24 × 16이므로 표의 X/Y는 **1/16 픽셀 단위**로 보이며, 원본(PS2) 폰트 텍스처가 14×10 칸(칸당 18×24 px)이었음을 시사한다 `추론`. HD 아틀라스(21×11, 48×64 @1024)와는 배치가 달라서, 표의 X/Y와 HD 셀의 대응은 exe 밖(HD 교체 계층)에서 처리된다 `미확인`.

**적용 범위 (2026-09-21 확인):** `mod\kh1\exchange\US_font_data_tbl.bin`은 로드되어 적용된다. 그러나 **상점 목록 같은 UI 글꼴만** 이 표의 폭을 따른다. 대화창(kanji.knj 글꼴)의 폭은 8절의 테이블에서 온다고 추정된다.

## 8. `exchange\UK_kanji.knj` 의 폭 테이블 `확정`(구조) / `추론`(역할)

263,616 B. 앞부분은 4bpp 비트맵 데이터, 끝부분은 다음과 같다.

| 오프셋 | 내용 |
|---|---|
| `0x40004` | 팔레트. `30 30 30 80`, `88 88 88 80`, `F8 F8 F8 80` 등 회색 계조 + 알파 `0x80` (PS2 형식) |
| `0x40080` ~ 파일 끝(`0x405C0`) | **글리프별 1바이트 폭 테이블, 1344개** = 336 x 4 (`T[idx]` = 오프셋 `0x40080 + idx`). 비제로는 마지막이 idx 1228 |

- **`T[idx]`와 US 표 `[+6]`(폭)의 상관계수 r = 0.901** (rec 11–62, 이동량 0). 값은 대략 표 폭 + 2.6 (`A` 11→14, `I` 7→8, `e` 10→12, `t` 9→12).
- **336칸(=21×16) 블록 4개**가 반복된다 (`0`, `336`, `672`, `1008`부터). 블록 안 채워진 구간은 `0..125`, `140..220`이고 `126..139`, `221..335`는 0이다. 네 블록의 구조가 같다. knj1의 네 사분면이 같은 것과 부합한다.
- 채워진 구간 합계 828개.
- 블록당 336칸 = 21열 × 16행. knj0(1024×1024, 셀 48×64)은 정확히 21×16 = 336칸이며, 여태 쓰지 않은 `221..335`(115칸)가 knj0의 빈 영역과 일치한다 `추론`.

**2바이트 코드로 도달 가능한 idx** (exe 7절 공식 `((b0<<8)|b1) - 0x1820`, `b1 ≥ 0x20`):

| b0 | idx 범위 |
|---|---|
| `0x19` | 256–479 |
| `0x1A` | 512–735 |
| `0x1B` | 768–991 |
| `0x1C` | 1024–1247 |
| `0x1D` | 1280–1503 |
| `0x1E` | 1536–1759 |
| `0x1F` | 1792–2015 |

1바이트 코드는 idx 0–220 (`0x20`–`0xFC`) + 221–223 (`0xFD`–`0xFF`). 224–255, 480–511 등은 `b1 < 0x20` 이 필요해 실용적으로 도달 불가.

테이블 길이가 1344(336 x 4)이므로 **idx 1343이 상한**이다 `확정` (파일 길이 263,616 - 0x40080 = 1344).

## 9. 폰트는 둘이다 / 대화창 글리프 셀 계산 (exe) `확정`

| | UI (상점 목록 등) | 대화창 |
|---|---|---|
| 폭·좌표의 출처 | `exchange\US_font_data_tbl.bin` | `exchange\UK_kanji.knj` 꼬리 폭 테이블 |
| 셀 배치 | 표의 X/Y: 14열 x 10행, **셀 18 x 24** (`sysfont`) | 공식: 21열 x 16행, **셀 24 x 32** (`kanji.knj`) |
| 근거 | 5차 (`e` 폭 → 목록만 변함) | 6차 (`e` 폭 → 대화창만 변함) |

표의 피치 288 = 18 x 16, 384 = 24 x 16이고 대화창 아틀라스 셀 24 x 32 (knj0은 2배 = 48 x 64)인 것이 서로 다른 이유가 이것이다. 위 7절의 디코드 루틴 6개는 모두 US 표를 읽는 UI 쪽이다.

**대화창 셀 계산 함수** RVA `0x175AE0` (0x948 바이트), 호출자 `0x1756BA`, `0x175A6D`:

```text
code < 0x2710 (10000)            일반 글리프 (0x2710 이상은 아이콘 등 별도 경로)
page = code / (21 * R)           R = 전역 [0x4DE830] (16로 추정)  -> 336칸 단위
cell = code - page * 336
row  = cell / 21,  col = cell % 21          ; 0x30C30C31 = 21로 나누는 매직 상수
x    = col * 24 * 16 + 8                    ; 1/16 픽셀 단위
y    = row * H * 16 + 8                     ; H = 전역 [0x4DE834] (셀 높이, 32로 추정)
code == 9999                     공백 처리
```

- 페이지는 4개 (idx 0-1343). 폭 테이블의 336 x 4 블록과 일치한다.
- **`idx >= 221`을 걸러 내는 조건은 이 경로에 없다.**
- 호출자는 16비트 글리프 코드가 `0x27D8`(10200) 미만이면 일반 글리프 경로로 보낸다.
- `0x2D0C37`은 글리프 코드를 UTF-16 문자열로 변환한다. 표의 `[+8..9]` 유니코드 필드를 읽는 유일한 함수이며 (`[표 + idx*16 + 8]`), 제어 코드는 길이(1~5바이트)만큼 건너뛴다.
- `kanji.knj` 로더 `0x28C390`은 언어별 경로(`exchange/UK/kanji.knj` -> `exchange/UK_kanji.knj`, `/`를 `_`로 치환)를 만들어 파일을 통째로 읽는 범용 로더다. 구조 해석은 하지 않는다.

## 10. 대화창 글리프 그리기 규칙 `확정` (10차, 11차)

**색:** 셀의 각 픽셀은 **RGB = 회색(최대 `0x80`) x 커버리지, 알파 = `FF`** 로 쓴다 (커버리지 0인 픽셀은 전부 0). **알파만 채우면 화면에 나타나지 않는다.** 원본 글리프는 이 위에 검정 윤곽(RGB 0, 알파 `FF`)과 알파 계조 그림자를 더한 구조다 (원본 `e` 셀: 회색 채움 `0x80` 115px, 검정 불투명 119px, 알파 계조 31단계).

**위치:**

```text
knj0 @4096   x0 = col*192 + 4,  y0 = row*256 + 4,  크기 192 x 256   (4096 밖은 잘림)
knj0 @1024   x0 = col*48 + 1,   y0 = row*64 + 1,   크기 48 x 64
knj1 사분면  x0 = qx*2048 + col*96 + 2,  y0 = qy*2048 + row*128 + 2,  크기 96 x 128   (대화창은 knj1을 읽지 않으나 일관성을 위해 함께 수정)
col = (idx % 336) % 21,   row = (idx % 336) / 21
```

- 수정 대상 DDS 20개: `mod\kh1\remastered\kanji.knj\*_kanji_knj{0,1}.dds`, `mod\kh1\remastered\exchange\UK_kanji.knj\*_kanji_knj{0,1}.dds` (5개 언어 x 2개 경로 x 2장). 게임이 실제로 읽는 것은 UK 쪽이지만 나머지도 같은 내용으로 유지하면 안전하다.
- DDS는 4096x4096 B8G8R8A8, 헤더 128 B, 행 피치 16384 B. 픽셀 오프셋 = `128 + y*16384 + x*4`.

**폭:** `UK_kanji.knj`의 `0x40080 + idx` 1바이트. 화면에서 1단위 = 약 2.45px, 한글 한 칸(셀 폭 24단위)의 자연폭은 약 22~24.

**메시지 안전 규칙:** 문자열 길이를 바꾸지 않는다. 남는 자리를 `00`으로 채우면 뒤 문자열 번호가 밀릴 위험이 있으므로 `01`(공백)로 채운다. 종결자는 원래의 `00`을 그대로 둔다.

## 11. exchange 의 메시지 파일 형식 `확정` (37차, 38차)

대화창과 같은 1바이트 문자표를 쓴다. 게임(영어)은 `exchange/UK_*` 를 읽는다 (exe 문자열 `exchange/%s_...`).

| 형식 | 파일 | 도구 |
| --- | --- | --- |
| u32 메시지 수 + 메시지 + 00/CD 패딩 (EvMsg 머리말 없음) | HZRankingMsg, PresentMessage, ShopMessage, gumi_shop_msg, *_cup, item_shop_msg | `evmsg.parse_plain` |
| 데이터 + u16 오프셋 표 (별도 파일) | SAWDMSG+SAWDOMSG (월드맵 메뉴), SAWEMSG+SAWEOMSG (구미 쉽 비행 대사), wname_data+offset (월드 이름), wsysmsg_data+offset (구미 쉽 게이지), name_mes+name_o_mes (이름 입력) | `evmsg.parse_ofs` / `serialize_ofs`, `evmsg_export.OFS_PAIRS` |
| 같은 형식, 데이터와 표가 다른 폴더 | `remastered/gumi/SASAMSG.BIN/UK_SASAMSG.BIN` + `exchange/UK_SASAOMSG.BIN` (구미 차고), `gumi_mes_data`+`gumi_mes_ofs` (구미 블록 이름, exe 에 US_ 없음) | 미적용 (HD 메뉴 글꼴) |

오프셋 표: u16 값 중 데이터 안을 가리키는 것만 오프셋이다. 0 은 빈 칸 또는 첫 메시지, CD/공백(0x2020) 은 쓰레기로 그대로 둔다. 조각 중간을 가리키는 값은 SASAMSG 에만 있다 (12585). SAWEMSG 는 메시지 끝 `00` 뒤에 `00 91 00` 같은 부가 바이트가 있어 표가 안 가리키는 조각이 생긴다 (그대로 둔다). 원래 크기보다 짧아지면 CD 로 채워 크기를 지킨다 (로더가 고정 버퍼인지 미확인).

**0x0D 코드 (월드맵/구미 파일, 41차 정정)**: 시스템 글꼴 문자열에서 `0x0D lo hi` 는 3바이트 x 이동이다 (exe 확정, exe-analysis 5-1절). 대화창 규칙(4바이트)으로 보이는 evmsg 표기 `[0D 0C 00 2F]nd of the World` 의 넷째 바이트는 실제 글자(E)다. 40차 번역에서 넷째 바이트를 `01`(공백)로 바꾼 곳은 41차에서 x 이동 값으로 위치를 다시 맞췄다.

**시스템 글꼴로 그려지는 exchange 파일 (39차 화면, 40차부터 `SYSFONT_FILES` 로 시스템 글꼴 코드로 넣음)**: SAWDMSG(월드맵 메뉴), wname(월드 이름), name_mes(이름 입력), wsysmsg(추론), SAWEMSG(비행 대사, exe 0x1f5110 -> UI 글꼴 모듈 0x2d35d0/0x2d2970 으로 확인). 

**메뉴 아이템 이름·설명은 exchange 가 아니다**: `remastered/btltbl.bin/UK_Word.bin` (이름), `UK_ItemHelp.bin`, `UK_AbilityName.bin`, `UK_AbilityHelp.bin`, `menu/uk/sysmsg.bin/UK_sysmsg.binl` ("Message v361"). 같은 문자표지만 시스템 글꼴(sysfont)로 그려진다 (known-issues).

**메뉴 이름·설명 (42차 적용)**: `remastered/btltbl.bin/UK_{Word,ItemHelp,AbilityName,AbilityHelp}.bin` = 0x00 끝 시스템 글꼴 문자열이 순서대로 이어진 목록. 머리말·오프셋 없음.

| 파일 | 게임이 읽는 수 | 들어가는 곳 (exe 0x28f9d0) |
|---|---|---|
| UK_Word.bin | 512 (명령, 마법, 아이템, 액세서리, 무기, 리액션 명령) | `0x2d22f98` u32 x 512 |
| UK_ItemHelp.bin | 255 | `0x2d22d38` 표 +0xC (0x14B 레코드) |
| UK_AbilityName.bin / UK_AbilityHelp.bin | 65 / 65 | `0x2d36d48` 표 +4 / +8 (0xC 레코드) |

- 문자열 나누기는 exe `0x28f820` 규칙 (evmsg.code_len_ui / split_ui): 끝 0x00·0x10, 0x03 0x07 0x0C 0x0F 2바이트, 0x08 5바이트, 0x0B 4바이트, 0x0D 0x0E 0x11~0x14 3바이트, 그 외 제어 1바이트, 0x15~0x1F 2바이트 글자.
- 정해진 수 뒤의 문자열(UK_ItemHelp 꼬리 등)은 읽히지 않는다 -> 그대로 둔다. 길이 제한 없음 (자산 데이터를 통째로 두고 각 문자열 포인터만 등록). 짧아지면 CD 로 원래 크기를 채운다.
- 자산 이름 비교는 `Word.bin` 등 접두어 뒤 이름 -> `UK_btltbl_bin_*.bin` 은 이름이 달라 쓰이지 않는다 (`추론`). US_ 판은 문자열 수가 모자라 대상에서 뺐다.
- **대화창 [0E xx] 삽입**: 대화창 msg_layout 의 0x0E (exe 0x176df3) 가 Word(아이템 이름, 0x28f9b0)·AbilityName(0x28f8f0) 문자열을 대화창 글꼴로 끼워 넣는다 ("Obtained [0E 01]."). 그래서 이 두 파일에 쓰인 한글은 두 글꼴에서 같은 코드여야 한다 -> `evmsg_export.SHARED_FILES`, build_ko 가 두 글꼴 모두 쓸 수 있는 idx 469개 중에서 먼저 배정, verify_build 가 확인.

**메뉴 시스템 메시지 "Message v361" (42차 적용)**: `remastered/menu/uk/sysmsg.bin/UK_sysmsg.binl` (= `menu/sysmsg.bin/UK_sysmsg.binl` 과 같은 내용). 머리말 `Message v361` + u32 수(488) + u32 표 위치(0x20) + u32 데이터 위치(0x3F2) + u32 표 크기(0x3D2 = 489칸) + u32 데이터 길이. 표 = u16 데이터 안 오프셋, 데이터 = 시스템 글꼴 문자열 (code_len_ui). `evmsg.parse_v361` / `serialize_v361`, `evmsg_export.V361`.
- exe `0x2d1570`: 언어별 경로 표 `0x52a888` -> `menu/uk/sysmsg.bin`, 자산 `sysmsg.binl` 을 **고정 버퍼 `0x2E1AC60` (0x4800 = 18,432B)** 에 복사, +0x14/+0x10 을 UI 메시지 표 `0x2e1ac48/50` 로 건다. 파일이 18,432B 를 넘으면 안 된다 (build 가 확인). 42차 결과 12,464B.
- 대화창 [0E xx] 삽입 대상이 아니다 (0x0E 하위 코드: 01/05/06/07/20~23 = Word, 04 = AbilityName, 02 = gumi_mes, 03 = 세이브 데이터 이름, 10~17 = 숫자).

**장소 이름 `exchange/UK_allarea.nam` (42차 적용)**: Shift-JIS 전각 문자열 표 (형식은 tools/allarea.py 머리말). 메뉴 위·세이브 파일에 쓰인다. 시스템 글꼴 레코드를 +0..1 의 Shift-JIS 코드로 찾으므로 한글은 가짜 코드 F0~F7 xx 로 넣고, 찾는 레코드 수를 메모리 패치로 1024 로 늘린다.

**지미니 메모 (44차 적용)**: `remastered/menu/md_{dic_msg,syno,anthem,jiminy}.kmb/UK_*.kmb` = u32 수 + 문자열 (0x00 끝, `[0F 01]` 쪽 넘김). 본문은 **대화창 글꼴**로 그려진다 (44차 화면 확인) -> 두 글꼴 공유 코드로 배정, 줄 폭은 대화창 폭 기준 240 (사전 오른쪽 쪽 1~2줄 145). `md_memo_sysmsg.bin/UK_md_memo_sysmsg.binl` = Message v361. 로더 0x2fbb80 이 메모리 풀 구역에 덮어쓰므로 원본 크기 이내로.
